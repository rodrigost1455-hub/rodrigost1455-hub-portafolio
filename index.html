how I work

quality discipline · engineering discipline

Automotive quality

  • 8D, guided. Containment, root cause and verification are steps the tool enforces, not a form someone fills in afterwards.
  • SPC before opinions. P-Charts with UCL, Cp/Cpk, paired measurements and hypothesis tests before anyone argues about a cause.
  • PPAP-style discipline. Official formats kept, releases (PCI) and audits (LPA) traceable, evidence attached to every claim.
  • Calibrated ≠ validated. Check the measurement system at the point of use before blaming the process.

Engineering

  • Test what it must refuse. YIA is evaluated on out-of-scope questions as well as correct answers.
  • Security by design. PBKDF2 password hashing, lockout, CSRF, CSP, roles and an audit log in QualityHub, with zero third-party packages to review.
  • Document the trail. Architecture, status and known limits written down, so IT, Quality and Metrology can all review the same thing.
  • Honest status. Pilot, prototype, case study or live: each project says which one it is.

// case study · automotive quality · web platform

QualityHub — one web platform for the plant's quality work, with zero third-party packages.

problem

Customer complaints, RMA/scrap, lessons learned, PCI releases and failure analysis lived in scattered Excel workbooks. The first fix, an Excel macro, died when corporate antivirus blocked the .exe.

solution

A web app: browser → Python web server (users, roles, sessions) → fixed-command engine → one SQLite per department, with a verified nightly backup and nothing to install on PCs. Guided 8D, P-Chart/PPM, 48 h failure analysis per part, warranty, LPA audits and overdue-8D e-mail alerts, in the plant's official formats.

results

~25,000 lines, no pip/npm, no CDN, one inbound port. PBKDF2-SHA256 (600,000 iterations), lockout after 5 attempts, HttpOnly/SameSite cookies, CSRF protection, 7 roles, audit log, CSP.

status

Approved by management for a phased rollout; in architecture and cybersecurity review with IT; controlled pilot inside Quality. Not in plant-wide production.

learned

Zero dependencies wasn't a style choice: it was designed to make the security review easy.

~25Klines · 0 deps
Built to survive an IT review, not just a demo: every control above is listed in the case study.

YIA — a RAG assistant that cites its source or says it doesn't know.

problem

Answers live inside work instructions, control plans, complaints and lessons learned. An assistant that guesses is worse than none.

solution

Read → split into chunks → embeddings → similarity search (top 8) → answer written only from those fragments, with the source cited. No relevant fragment, no answer. Python + Streamlit + NumPy, no third-party AI frameworks, ~2,900 lines.

results

Own evaluation (61 questions): 42/42 exact data, 42/42 correct source cited, 14/14 out-of-scope questions rejected. Limits: it sometimes adds detail the document doesn't state, and it doesn't read images.

status

Prototype (proof of concept) in the cloud on de-identified documents; under IT review. Not a production product.

learned

Refusing to answer is a feature, so out-of-scope questions had to be tested as deliberately as correct ones.

42/42exact + cited
Self-graded, small, and stated as such. The failure modes are published next to the score.

// case study · data science for test validation

A −0.47 Ω bias hiding behind a Cpk of 0.47.

problem

An end-of-line (EOL) test station was rejecting good parts, and line A showed a Cpk of 0.47 on the same resistance that line B measured at Cpk 1.5.

method

Python parsers for two different log formats into one schema; detection of overload sentinels (9.9E37); Power BI dashboard (Cp/Cpk, scatter with limits, histogram with normal curve); per-line analysis.

finding

A systematic ≈ −0.47 Ω bias at one station, confirmed with bench measurements paired by serial number (n=46, r=0.83) and a second independent sample weeks later. Slope indistinguishable from 1 (p=0.96): an additive offset, not a gain error. Bad contact, assembly stress and single-channel faults were ruled out.

second finding

The LCR meter's calibration certificate covered standard points but never the real operating range (~27 Ω, ~90–100 nF).

learned

Calibrated is not the same as validated at the point of use.

n=46paired · r=0.83
Applied statistics, not a dashboard: Cpk, regression and hypothesis tests, then root cause communicated to Metrology.

// case study · sole engineer · 2025

Watson ML Classifier — 100% precision on phantom-current sensor defects.

context

PHEV current sensors from a sensor supplier were showing intermittent defects on End-of-Line testers — and the supplier was pushing back on the data, calling them phantom readings. We needed a defensible classifier built on the actual EOL tester output, not on supplier reports.

decision

Skip notebook-only experiments. Build a real pipeline: a custom parser that extracts 34 features from raw EOL TXT files, AutoAI-driven model selection landing on a cross-validated Decision Tree, deployed to IBM Watson ML, and consumed by a Next.js front-end through a secure server-side API route (so the IBM key never reaches the browser).

impact

100% precision on holdout · supplier dispute resolved with auditable evidence · live web app for plant engineers to score new sensors on demand.

34features
From raw TXT to deployed endpoint — feature engineering, training, AutoAI selection, deploy. The pipeline is the product.
